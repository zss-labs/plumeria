---
title: 'Module architecture'
description: 'Organize styles as exported modules, share them across packages, and refactor them without changing the output.'
---

Styles are module exports. A style used by one file stays in that file; a style
used by more than one file moves to a module and is exported, and every file
that needs it imports it. Each style is defined once, the way a **Go package** or a
**Java class** is the one place its members are declared.

## Layout

```
app/
└─ page.tsx
components/
├─ Card.tsx
└─ Profile/
   ├─ Profile.tsx
   └─ styles.ts
styles/
├─ theme.ts
├─ tokens.ts
├─ layout.ts
└─ text.ts
```

`styles/` only exports. It imports no components and renders nothing, so
dependencies run one way: `styles/` ← `components/` ← `app/`.

## Values

Values that styles refer to live apart from the styles themselves.

```ts title="styles/theme.ts"
import * as css from '@plumeria/core';

export const theme = css.createTheme('.dark', {
  text: {
    default: '#333',
    theme: '#eaeaea',
  },
});
```

```ts title="styles/tokens.ts"
import * as css from '@plumeria/core';

export const breakpoints = css.createStatic({
  sm: '@media (max-width: 640px)',
});
```

## Shared styles

```ts title="styles/layout.ts"
import * as css from '@plumeria/core';
import { breakpoints } from './tokens';

export const layout = css.create({
  stack: {
    display: 'flex',
    flexDirection: 'column',
    gap: 16,
    [breakpoints.sm]: {
      gap: 8,
    },
  },
});
```

```ts title="styles/text.ts"
import * as css from '@plumeria/core';
import { theme } from './theme';

export const text = css.create({
  heading: {
    fontSize: 24,
    fontWeight: 700,
    color: theme.text,
  },
});
```

## Using them

A file that writes `classStyle` is compiled whether or not it imports
`@plumeria/core`. A file that hands a style to a component through any other
prop has to import it; that import is how the compiler finds the file. Keeping
the import in every file that uses Plumeria is always safe, and it is the
fastest path: the compiler accepts such a file without looking any further.

```tsx title="app/page.tsx"
import { layout } from '../styles/layout';
import { text } from '../styles/text';

export default function Page() {
  return (
    <main classStyle={layout.stack}>
      <h1 classStyle={text.heading}>Hello</h1>
    </main>
  );
}
```

A style only one component uses stays in that component's file and is not
exported:

```tsx title="components/Card.tsx"
import * as css from '@plumeria/core';

const styles = css.create({
  card: {
    padding: 16,
    borderRadius: 8,
  },
});

export const Card = () => <div classStyle={styles.card} />;
```

When a component's styles grow long enough to crowd its markup, they can move
to a `styles.ts` next to it. The output does not change, and only that
component imports them. Once another component needs one of them, it moves to
`styles/`.

```ts title="components/Profile/styles.ts"
import * as css from '@plumeria/core';

export const styles = css.create({
  profile: {
    display: 'flex',
    gap: 12,
  },
  avatar: {
    width: 40,
    height: 40,
    borderRadius: '50%',
  },
});
```

```tsx title="components/Profile/Profile.tsx"
import { styles } from './styles';

export const Profile = () => (
  <div classStyle={styles.profile}>
    <img classStyle={styles.avatar} src="/avatar.png" alt="" />
  </div>
);
```

## Imports

A namespace import reads a definition by name, as a named import does:

```ts title="styles/layout.ts"
import * as css from '@plumeria/core';
import * as tokens from './tokens';

export const layout = css.create({
  stack: {
    gap: 16,
    [tokens.breakpoints.sm]: {
      gap: 8,
    },
  },
});
```

Every read is written in place, so the compiler has to see which definition is
read. A string key, destructuring, a rest element or passing `tokens` as a whole
stops the build.

An import whose names are all compiled away is removed from the output, so the
bundler never loads the module through it. An import still read at runtime,
rendered as a component or re-exported stays. A module that also has to run on
import, such as one importing a global stylesheet, gets an import of its own:

```ts
import './tokens';
```

## Across packages

A package shares its definitions by pointing a `plumeria` export condition at
its TypeScript source:

```json title="package.json"
{
  "name": "@acme/tokens",
  "exports": {
    ".": {
      "plumeria": "./src/index.ts",
      "types": "./src/index.ts"
    }
  }
}
```

```ts title="src/index.ts"
import * as css from '@plumeria/core';

export const brand = css.createStatic({
  primary: '#0b5fff',
});
```

An app that lists the package in its dependencies reads it like a local module:

```tsx title="Button.tsx"
import * as css from '@plumeria/core';
import { brand } from '@acme/tokens';

const styles = css.create({
  button: {
    backgroundColor: brand.primary,
  },
});
```

The compiler follows the condition through subpath and pattern exports such as
`@acme/tokens/colors`, and into packages linked from a pnpm store.
`dependencies`, `devDependencies`, `peerDependencies` and `optionalDependencies`
all count. A package without the condition is not read.

The import compiles away, so a package that exports only definitions can ship
its source alone, as [`@plumeria/wind`](/docs/api-reference/wind) does. One that
also exports runtime code keeps a `default` condition for it.

## Refactoring is free

Where a style is written does not reach the output. A class name is derived
from the property and the value alone, so moving a style into a module
compiles to the same class names and the same CSS.

Before, in one file:

```tsx title="app/page.tsx"
import * as css from '@plumeria/core';

const layout = css.create({
  stack: {
    display: 'flex',
    flexDirection: 'column',
    gap: 16,
  },
});

export default function Page() {
  return <main classStyle={layout.stack}>Hello</main>;
}
```

After, moved to a module:

```ts title="styles/layout.ts"
import * as css from '@plumeria/core';

export const layout = css.create({
  stack: {
    display: 'flex',
    flexDirection: 'column',
    gap: 16,
  },
});
```

```tsx title="app/page.tsx"
import { layout } from '../styles/layout';

export default function Page() {
  return <main classStyle={layout.stack}>Hello</main>;
}
```

Both compile to:

```tsx title="app/page.tsx (output)"
<main className="xxp6epoh xi0vg1kw x2b1m2la">Hello</main>
```

Moving a style into a module, splitting a module, or merging two of them never
changes what the browser receives, so the structure can follow the code as it
grows. Composition across modules is resolved at build time as well; see
[Composition laws](/docs/composition-laws) for the rules a merge follows.
